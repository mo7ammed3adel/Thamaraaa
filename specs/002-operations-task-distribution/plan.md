# Implementation Plan: Operations & Task Distribution System

**Branch**: `002-operations-task-distribution` | **Date**: 2026-04-23 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `specs/002-operations-task-distribution/spec.md`

## Summary

Build incremental enhancements to the existing CRM operations system to support: (1) task flag/return from agents back to Team Leaders, (2) task reassignment within teams by Team Leaders, (3) Warning resolution by the Warning creator, and (4) client reassignment between Account Manager Agents by the Head Account Manager. The existing codebase already covers ~80% of the spec requirements — this plan focuses exclusively on the remaining 20%.

## Implementation Phases

### Phase A: Schema Migration (foundation)

1. Add 3 columns to `Task` model: `flagReason`, `flaggedAt`, `flaggedByUserId`
2. Add 2 columns to `Warning` model: `resolvedAt`, `resolvedByUserId`
3. Run `prisma migrate dev`
4. Verify existing functionality is unaffected

**Dependencies**: None
**Risk**: Low — only nullable column additions, no breaking changes

### Phase B: API Endpoints (4 new routes)

1. `POST /api/tasks/[id]/flag` — validates agent ownership, sets flag fields, nulls agentId, reverts status to pending, sends Pusher event + notification
2. `POST /api/tasks/[id]/reassign` — validates Team Leader authority, checks new agent is valid target role, updates agentId, sends Pusher event + notification
3. `POST /api/warnings/[id]/resolve` — validates creator identity, updates status to Resolved, sets resolvedAt/resolvedByUserId, sends Pusher event
4. `POST /api/projects/[id]/reassign-am` — validates Head AM role, updates accountManagerId, creates ProjectLog, sends notifications

**Dependencies**: Phase A (schema must be migrated first)
**Risk**: Medium — permission validation must be thorough

### Phase C: New UI Components (4 modals/buttons)

1. `TaskFlagModal` — textarea for reason, submit triggers POST `/api/tasks/[id]/flag`
2. `TaskReassignModal` — dropdown of team agents, submit triggers POST `/api/tasks/[id]/reassign`
3. `WarningResolveButton` — single button, confirms before POST `/api/warnings/[id]/resolve`
4. `ClientReassignModal` — dropdown of Account Manager Agents, submit triggers POST `/api/projects/[id]/reassign-am`

**Dependencies**: Phase B (API endpoints must exist first)
**Risk**: Low — follows existing modal patterns (CreateWarningModal, DistributeModal)

### Phase D: Dashboard Integration

1. **Head Account Manager** (`HeadAccountManagerClient.tsx`) — add `ClientReassignModal` trigger on client detail page
2. **Account Manager** (`AccountManagerClient.tsx`) — add `WarningResolveButton` on warning cards where user is the sender
3. **SEO dashboards** (`SeoClient.tsx`) — add `TaskFlagModal` for agents, `TaskReassignModal` for Team Leaders
4. **Social Media dashboards** — add same flag/reassign patterns
5. **Media Buyer dashboards** — add same flag/reassign patterns
6. **Design dashboards** — add same flag/reassign patterns for Graphic Design, Motion Graphic, UI/UX

**Dependencies**: Phase C (components must be built first)
**Risk**: Medium — must carefully integrate into each role's existing view logic

### Phase E: Verification & Polish

1. Test all 4 new flows end-to-end (task flag, task reassign, warning resolve, client reassign)
2. Verify Pusher events fire correctly and dashboards update in real-time
3. Verify permission enforcement (wrong role gets 403)
4. Verify data preservation during client reassignment
5. Build verification (`npm run build` must pass cleanly)
